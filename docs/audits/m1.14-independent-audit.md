## 4. Validation and portability summary

**Split.** Shape is handled by the precompiled Ajv validator and meaning by
`validateDrill()`. The split is clean, and semantic rules do not duplicate
schema rules. Issues are `{ code, paths, message }`, codes are a `const`
tuple with a derived union type, and paths are property-accessor strings that
name every party (both balls in an overlap, every duplicate ID). Output order
is deterministic.

**Pipeline.** The CLI runs read → `JSON.parse` → schema → `validateDrill`, and
each failure category is distinct (`apps/cli/src/validate.ts:63-97`). A
schema-invalid document never reaches `validateDrill`, which assumes valid
shape and throws on `{}` (F5).

**Geometry probes** (beyond the existing tests):
- The exact boundaries `x = r`, `x = 1 − r`, `y = r` and `y = W/L − r` on 9 ft
  are all accepted. The IEEE-754 values of `1.125/100` and its complements
  equal the decimal literals, so there is no false rejection.
- Frozen pairs exactly one diameter apart (axis-aligned and diagonal) are
  accepted. The 1e-12 slack applies to overlap only and cannot hide a real
  overlap.
- `1e400` parses to `Infinity`, and the schema rejects it (Ajv's `number` is
  finite).
- The circle-in-rectangle test uses the bounding box, which is exact for an
  axis-aligned legal area.

**Portability.**
- `packages/core` has one dependency, `@pool-drill-gen/schema`.
- `packages/schema` has no runtime dependencies. Ajv and
  `json-schema-to-typescript` are devDependencies.
- The generated validator imports nothing. Its only dynamic construct is
  `new RegExp` for the `createdAt` pattern, which is permitted in Workers.
  There is no `eval`, `Function` or `ajv.compile` in any `src`.
- `check:browser` bundles `core` and `schema` `dist` with esbuild using
  `platform: browser`, then executes the bundle in a `vm` context with
  `codeGeneration.strings = false`. That is real evidence of no runtime code
  generation. It is not a real browser or Worker runtime.
- File I/O exists only in `apps/cli/src/validate.ts:11`.
- The dependency direction schema → core → cli holds in both manifests and
  imports.

**Checker blind spots** (theoretical, none exploited): see F6.

## 5. Schema and generated-type assessment

- **Invented semantics.**
  - `format`, `skills`, `difficulty`, `tags` and `extensions` were approved in
    the M1.3 scope (#4).
  - `game` is in neither an ADR nor #4. #13 names it as `show` output. It is
    optional, an open string and inert (F7).
  - No `marker` role, no constraints bag, no spin/speed fields, no progression
    model, and `shot.type` has exactly one value, `pot`.
- **Conditionals.** `pot ⇒ pocket` and `count ⇒ attempts, target` use
  `if`/`then` as ADR-0009 prescribes. The conditionals are correct in Ajv.
- **Generated types.** These are faithful for what `json-schema-to-typescript`
  can express. Conditional requirements are lost (`Shot.pocket?`,
  `Success.attempts?`/`target?`, `drill.ts:200,222,226`), and because `Point`
  carries an index signature, a `CircleRegion` is structurally assignable to
  `Point`. These gaps do not change which documents are accepted or rejected
  (Ajv is the gate), but TypeScript consumers must rely on the runtime guard
  (F4).
- **Parallel models.** There is no hand-maintained domain model. Core aliases
  generated types (`geometry.ts:28-41`), and `--strict` derives the known
  property set by walking the canonical schema (`strict.ts:12,47`).
- **Reproducibility.** `pnpm schema:generate` reproduces both artifacts
  byte-for-byte. `check:generated` compares the whole `generated/` directory
  to `HEAD`, including untracked files.

## 8. Findings

### BLOCKER

**B1 — ADR-0009 `target ≤ attempts` is enforced nowhere.**
- **Where:**
  - `packages/core/src/rules.ts` has no success rule.
  - `packages/core/src/validation.ts:37-75` has no code for it.
  - The schema delegates the rule to core in
    `packages/schema/src/schema/drill.schema.json:5` and `:307`.
  - `packages/schema/test/schema-vs-semantic.test.ts:202-205` asserts that
    the schema accepts it "enforced in core", but no core test exists.
- **Requirement:** ADR-0009's field table: "`target` … integer ≥ 1, and
  `target ≤ attempts`". The schema's own contract also says core checks it.
- **Reproduction:**
  ```
  # stop-shot-repetition with "success": {"mode":"count","attempts":3,"target":10}
  $ pooldrill validate target-gt-attempts.pooldrill.json   → Valid drill: …   [exit 0]
  $ pooldrill show     target-gt-attempts.pooldrill.json   → Success: count (10 of 3 attempts)
  ```
  `validateDrillSchema` → `true`. `validateDrill` → `{ valid: true, issues: [] }`.
- **Impact:** an impossible success criterion validates. M4 practice logging
  would read it as authoritative. The schema/core split promises a rule that
  neither half implements.
- **Fix:**
  - Add one semantic rule in `rules.ts`. When `success.mode === "count"` and
    `target > attempts`, emit a new code (for example
    `SUCCESS_TARGET_EXCEEDS_ATTEMPTS`) with paths
    `["success.target", "success.attempts"]`.
  - Add it to `VALIDATION_CODES`, with focused core tests and a CLI
    semantic-failure test.
  - No schema or ADR change.
- **Blocks M1 exit:** yes.

### SHOULD-FIX

**S1 — The `tableSize` / `playingSurface` mismatch warning is not implemented.**
- **Where:** `docs/adr/0005-…md:39` ("`validateDrill()` warns on an
  implausible pairing") and `CLAUDE.md:159` ("mismatches warn"). `rules.ts`
  never reads `tableSize`, and `ValidationResult` (`validation.ts:113-116`)
  has no warning channel.
- **Reproduction:** `tableSize: "7ft"` with a 100×50 surface gives
  `validate --strict` → `Valid drill`, with no output on stderr.
- **Impact:** the only mitigation ADR-0005 offers for label/geometry drift is
  missing. Validity is unaffected, because geometry never uses the label.
- **Why not a blocker:**
  - The rule is advisory and changes no validity outcome.
  - No M1 issue scoped it.
  - Defining "plausible" without drifting toward the table registry ADR-0005
    rejected is a design decision.
  - The reviewer may escalate.
- **Fix:** add a warning severity (or a separate `warnings` array) to
  `ValidationResult` and one label-plausibility rule for the four documented
  profiles. Surface it in the CLI as a warning that leaves the exit code
  unchanged.
- **Blocks M1 exit:** no.

**S2 — The validation code name diverges from ADR-0003.**
- **Where:** `docs/adr/0003-…md:75` names `UNKNOWN_BALL_REF`, but
  `validation.ts:46` emits `UNKNOWN_BALL_REFERENCE`.
- **Impact:** a consumer written against the ADR will never match the code.
  No consumers exist yet, so renaming is cheapest now.
- **Fix:** rename the code to `UNKNOWN_BALL_REF` (code conforms to the ADR)
  and update the tests.
- **Blocks M1 exit:** no.

**S3 — `migrate()` is not on any read path.**
- **Where:** `apps/cli/src/validate.ts:85-97` does not call it. Unsupported
  versions are caught only by the schema `const`, which prints
  `/formatVersion: must be equal to constant` without naming the supported
  version.
- **Reproduction:** `formatVersion: "0.2"` through the CLI prints that
  message, while `migrate()` returns `FORMAT_VERSION_UNSUPPORTED`.
- **Impact:** ADR-0001 wants the migration path to be architectural. Today it
  is an exported function that no reader calls, and the CLI error is less
  informative than core's.
- **Fix:** call `migrate()` after `JSON.parse` and before the schema in
  `validateFile`, reporting its issues as their own category.
- **Blocks M1 exit:** no.

**S4 — The schema-vs-semantic boundary tests are not cross-checked against core.**
- **Where:** `packages/schema/test/schema-vs-semantic.test.ts` groups cases
  under "enforced in core, not here" (`:19, :78, :125, :202`). Several of them
  have no core counterpart:
  - `target > attempts` (B1).
  - A shot referencing the cue ball (`:71`). Core deliberately has no rule
    for this, and correctly so, because no ADR defines one.
  - An impossible calendar date.
- **Impact:** this is how B1 escaped. The labels assert enforcement that
  nothing verifies.
- **Fix:** pair each "enforced in core" case with a core assertion that it is
  rejected, or relabel the case "accepted by both: no rule in 0.1".
- **Blocks M1 exit:** no.

**S5 — CI does not gate merges.**
- **Where:** repository settings. The GitHub API reports `main` "Branch not
  protected" and an empty rulesets list.
- **Impact:** every M1.13 guarantee is advisory. A red PR can merge.
- **Fix:** require `Verify (Node 20.18.3)` and `Verify (Node 24)` on `main`.
- **Blocks M1 exit:** no.

### FOLLOW-UP

- **F1 — A normative document was amended inside an implementation PR.**
  - M1.8 (#26, `f598ac6`) rewrote `coordinates.md` §3.2 to add
    constraint-preserving quantization and changed §8.4 from `0.4888` to
    `0.4887`.
  - The change is correct: the old §8.4 value violated §4.1. It was also
    disclosed in the PR.
  - However, it refines ADR-0004's "rounded to 4 decimal places" with no
    decision record.
  - Recommend a short ADR-0004 addendum or erratum note. Not blocking.
- **F2 — The §8.2 7 ft example is outside the legal domain.**
  - `coordinates.md:334` lists `0.98558` for `1 − r`. The exact value is
    `0.985577`, and core correctly rejects it (`POINT_OUT_OF_BOUNDS`, probe
    P3).
  - `geometry-validation.test.ts:86` says "§8.2 … as written" but tests only
    the 9 ft row.
  - This is a documentation erratum. The implementation is correct.
- **F3 — No canonical writer or quantizer exists.**
  - M1 has no production serialization, so neither the §3.2 rules nor
    ADR-0006 writer preservation is exercised in shipped code. The round-trip
    test uses a local `JSON.stringify`, which proves only the in-memory
    representation.
  - Add a `serialize()` in core, with §3.2 rules 1–3 and the round-trip
    guarantee, before the first writing tool (M2 corpus tooling or M5
    editor).
- **F4 — Gaps in the generated types and type guard.**
  - Conditional requirements are absent from the generated types, and a
    region is structurally assignable to `Point`.
  - ADR-0008 says "one type guard in `packages/core`, used everywhere else".
    `isRegion` exists (`rules.ts:318`) but is not exported.
  - Export it before `packages/svg` needs it.
- **F5 — The `validateDrill()` precondition is enforced only by convention.**
  `validateDrill({})` throws a `TypeError`. The CLI guards this, but browser
  and Worker callers in M3 will need either a combined `parse → shape →
  meaning` entry point or a prominent contract.
- **F6 — Architecture checker blind spots.** These are theoretical, with no
  violation present. Each of the following passes `checkArchitecture` in
  `core`:
  - `const g = globalThis; g.process`
  - `Reflect.get(globalThis, "process")`
  - the AsyncFunction constructor
  - `import.meta.url`

  `layers` is hard-coded (`check-architecture.mjs:7`), so a new package is
  unchecked until it is added. The runtime `vm` probe partially compensates
  (code generation disabled, no Node globals). Extend both before M2 adds
  packages.
- **F7 — `game` is outside the approved field list.** It is in no ADR and not
  in #4. It is optional, inert and displayed by `show` (#13). Ratify it or
  drop it before `1.0`.
- **F8 — Corpus questions, correctly left open.**
  - A shot may reference the cue ball.
  - Two shots may pot the same ball under `any_order` or `strict`.

  Neither has an ADR rule, and core correctly invents none. Watch the M2
  corpus.

## 9. M1 exit decision

**FAIL.**

M1 is otherwise in strong shape:
- The build, 559 tests, the full `verify` gate, 11 negative probes and CI on
  Node 20.18.3 and 24 all pass.
- Core is demonstrably platform-neutral, with no runtime Ajv compilation.
- Unknown fields survive round trips.
- No M2+ functionality was found (no SVG, web, hosting, sharing, practice
  logging, generation, physics or editor code; packages are exactly `schema`,
  `core` and `cli`).
- Seven of nine ADRs are compliant.

However, **B1** is a demonstrated contradiction of ADR-0009: a drill whose
success criterion is mathematically unsatisfiable passes every validation
layer. That means "format 0.1 is … validated" in the #15 exit condition is
not yet met.

- **Issue #15 stays open.** Close it after B1 is fixed in separately reviewed
  work and re-verified. S1–S5 should be scheduled; none of them blocks.
- **M2 should not begin** until B1 is resolved.
